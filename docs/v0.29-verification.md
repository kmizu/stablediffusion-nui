# v0.29 verification record (2026-11-12)

Goal: faster generation with default settings and the same image. scala-torch `0.1.3-gh51` (commits a61b1c0 and a16446b).

The largest change is for prompts with a LoRA: SDXL 1024 with one LoRA took 55 to 59 s per image and takes 9 to 12 s now; batch
size 2 took 132.5 s and takes 19.7 s.

## Changes (scala-torch)

- Cross-attention to the text context (77 tokens) runs in the fused tensor-core attention kernel. The last key tile is staged in
  shared memory and the keys that do not exist are masked. Before, every cross-attention layer needed a score matrix, a softmax
  and four transposed copies. `SCALATORCH_CUDA_FUSED_ATTENTION_ANY_KEYS=0` keeps the old path.
- The residual adds of a transformer block are folded into the projection before them: the output starts as residual plus bias
  and cuBLAS accumulates the product on top. The bias of the GEGLU projection is added inside the GEGLU kernel.
  `SCALATORCH_CUDA_FUSED_RESIDUAL=0` keeps the separate passes.
- Float16 LayerNorm is one kernel that reads a row once (statistics and result); before, two kernels read it three times.
  `SCALATORCH_CUDA_FUSED_LAYERNORM=0` keeps the two kernels.

## Fix: text encoder with a LoRA (scala-torch a16446b)

The GPU text encoder did not upload the LoRA factors of its own layers. Every prompt with a text-encoder LoRA failed there
("CLIP CUDA path failed, using CPU: key not found: Parameter") and was encoded on the CPU by a scalar matrix product: about
20 s per SDXL prompt, twice per image, on every generation. Found by sampling the stacks of the request thread
(`SCALATORCH_SAMPLE_STACKS=1`): 20.2 s in `ScalarF32Kernels.gemmNT` under `Linear.apply`, while the U-Net kernels took 8.7 s.
The factors of the encoder are uploaded now and merged on the device, and the result cache has the factors and strengths in
its key (before, it was skipped whenever a LoRA was in scope).

SDXL 1024, 20 steps, `<lora:...:0.8>` (one SDXL LoRA with text-encoder and U-Net parts), second generation:

| Request | v0.28 ZIP | v0.29 ZIP |
| --- | --- | --- |
| 1 image | 58.7 s (55.1 s in a development run) | 11.7 / 10.8 s (9.1 s in a development run) |
| batch size 2 | 132.5 s | 19.7 s |

"CLIP CUDA path failed" lines in the log: 8 with v0.28, 0 with v0.29. The other programs on the desktop were using the GPU
during the ZIP runs. Image, same seed, looked at side by side: the picture of the GPU encoder and the picture of the CPU
encoder are the same character and composition (mean difference 4.8 of 255), and both differ from the image without the LoRA
as the LoRA intends (31.4).

Still slower with a LoRA than without (about 9 s against 7 s in the same session): the LoRA file is read again on every
request (about 1 s), the text encoders run again (0.5 s) and the VAE weights are uploaded again; VRAM is 12.7 GB against
7.3 GB. Not fixed here.

## Where the remaining time is

- cuBLAS Float16 matrix products reach 46 to 56 TFLOPS on this GPU for every shape tried, through PyTorch as well (2048 x 1280 x
  1280 up to 8192 x 8192 x 8192). The linear layers of SDXL (about 42 % of the U-Net time) run at about 53 TFLOPS in SDNUI, so
  they are at the limit of the library.
- GPU utilisation and power during generation are the same for scala-torch and for the PyTorch engine of NUI (94 %, 307 W).
- Three images in one request (three concurrent sessions) take 6.3 s each in the U-Net against 7.0 s for one alone, so a single
  stream leaves about 10 % of the GPU unused; not solved.
- Outside the U-Net an SDXL request spends about 0.9 s (0.34 s before sampling, 0.34 s VAE, 0.2 s after); not analysed yet.

## Image

Same seed, new paths against old paths (switched by the variables), looked at side by side for SDXL 1024 and SD1.5 512: the
same composition, no damage; fine detail differs (SDXL: the ribs of the sweater and the shadow on the wall). Mean difference
3.8 of 255 (SDXL), 2.7 (SD1.5), 2.9 (SD1.5 batch size 4). Against a Float32 image of the same seed the new image is not
consistently nearer or farther than the old one (SDXL 4.0 against 2.5, SD1.5 3.5 against 4.1), as expected of rounding
differences that an ancestral sampler amplifies. File counts were right (1, 4 and 8 files).

## Tests

- scala-torch `ffm` `testFull` on the GPU with cuDNN: 97 total, 95 passed, 2 skipped. New cases: key counts 17, 31, 77, 93 and
  154 for the fused attention (against Float32 and against the heads-major layout), residual folded into a linear layer, GEGLU
  with bias, LayerNorm rows of 7 to 2304.
- `models`, six suites that use the changed runtime: 33 total, 14 passed, 18 skipped, 1 failed. The failure
  (`CudaDiffusionAttentionSuite`, "validates shapes and score budget") is the same without these changes.

## Not covered

- LoRA was generated with one SDXL LoRA only (no SD1.5 LoRA, no LoRA without a text-encoder part, one strength).
- ControlNet, hires fix and the plugins that replace attention (HyperTile, Agent Attention, token downsampling, IP-Adapter,
  PAG, SAG) were not generated with this build. Their code paths keep the separate add; the model suites for them were skipped
  or not run.
- The GUI was not operated. No GPU with less than 24 GB. The fused kernels were run on an RTX 3090 only.
- reForge with its own speed options was not measured.

reForge was started for the measurement only and stopped afterwards (no listener on port 7869); its working tree is unchanged.
