# v0.18 verification record (2026-11-11)

## Fix: the first parallel Batch count request could fail with "job cannot begin publication"

Found while measuring v0.17: with count 4 the first request after a start sometimes ended in `generation failed: requirement failed: job cannot begin
publication` (the second request worked). Cause: the worker's "begin publication" check-and-set was not atomic, and the parallel count groups call it
from several threads. When two groups finished at the same moment, both passed the check and the second one failed the job's `require`.

Change (scala-torch `0.1.3-gh37`, `NativeWorker`): the check-and-set is under a lock. Regression test `NativeWorkerSuite` "threads of one job may begin
publication at the same moment" (8 threads x 20 jobs): **fails without the fix** (job 10: one failure) and passes with it.

## Classifier-free guidance as one batch of two

For plain requests (no LoRA, ControlNet, hooks, rescale or other guidance extras; guidance > 1) the negative and positive passes now run through the U-Net as
one batch of two instead of two passes. If the device runs out of memory, the old two-pass path is used. `SCALATORCH_CUDA_BATCH_GUIDANCE=0` switches it off.

Measured (RTX 3090, MCP, 20 steps, second run, same process; off = `SCALATORCH_CUDA_BATCH_GUIDANCE=0`):

| Request | off | on |
| --- | --- | --- |
| SD1.5 512, 1 image | 2.5 s | 2.2 s |
| SDXL 1024, 1 image | 10.9 s | 9.9 s |
| SDXL 1536, 1 image | 30.4 s | 29.5 s |
| SD1.5 512, count 4 (parallel) | 6.7 s | 6.5 s |
| SD1.5 512, count 2 x size 4 | 14.8 s | 13.9 s |

The gain is 3 to 12 %: one U-Net pass already keeps the GPU busy, so more batching helps little. Images differ slightly from v0.17 (fp16 kernels differ at
batch 2; SD1.5 seed 173: mean difference 1.2 of 255, same composition, both images looked at). Test: `CudaUNetSuite` "classifier-free guidance as one batch of
two matches the CPU predictor" (fp32, tiny U-Net, error < 1e-4; guidance 1.5 and 7.5, two timesteps).

Not covered: the tiny SDXL fixture is no longer in the repository, so the existing SDXL CFG oracle test (`CudaSdxlUNetSuite`) was skipped; SDXL was checked
by real generation only. The NUI test run has one failure that does not depend on this change: `PixelScrambleSuite` needs `python/.venv-test`, which does not
start here.
