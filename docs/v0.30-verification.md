# v0.30 verification record (2026-11-12)

Goal: remove what a generation with a LoRA still repeated on every request. scala-torch `0.1.3-gh52` (commit c1d1deb).

## Changes (scala-torch)

- A LoRA file that was read for the loaded model is kept (by file, size, modification time and dynamic rank; four files at
  most; dropped when another model is loaded). Before, the file was read and matched to the model on every request. Because
  the factor tensors stay the same, the text encoder cache applies to LoRA prompts again.
  `SCALATORCH_LORA_FILE_CACHE=0` reads the file every time.
- The key and value projections of the text context are computed once per sampling for the fused cross-attention (the context
  does not change between steps). `SCALATORCH_CUDA_CONTEXT_TOKENS_CACHE=0` computes them in every step.

## Measured

RTX 3090, MCP, fp16, 20 steps, Euler a, second generation of a process, cuDNN from a PyTorch installation. Other programs on
the desktop were using the GPU, so compare within a row only.

Development build against the extracted v0.29 ZIP, alternately, two rounds:

| Request | v0.29 | this build |
| --- | --- | --- |
| SDXL 1024, one LoRA, 1 image | 12.2 / 13.2 s | 10.1 / 10.3 s |
| SDXL 1024, 1 image | 8.6 / 7.1 s | 8.6 / 7.0 s |
| SD1.5 512, 1 image | 1.5 / 1.5 s | 1.5 / 1.5 s |
| SD1.5 512, batch size 4 | 4.1 / 4.0 s | 4.1 / 4.2 s |

- With a LoRA: about 2 to 3 s less per image (18 to 22 %). Since v0.28 (58.7 s) that is about 6 times faster.
- Without a LoRA: no measurable change in the total. In the profile the matrix products of the context ([154,1280,2048]) go
  from 2400 to 120 calls, 0.19 s to 0.012 s of kernel time for an SDXL image; the totals above vary by more than that.

On the extracted v0.30 ZIP (path with a space): SDXL with the LoRA 9.5 s, batch size 2 19.3 s (4 files for two requests);
SDXL 8.5 s, SD1.5 2.0 s, SD1.5 batch size 4 5.2 s (8 files). No request failed.

## Tests

`models`, five suites (text encoder, LoRA, transformer, U-Net, worker settings): 23 total, 11 passed, 12 skipped (they need
model files or other environment variables), none failed.

## Not covered

- One SDXL LoRA with one strength. No SD1.5 LoRA, no two LoRAs at once, no change of the LoRA file between requests (the key
  has size and modification time; not exercised), no prompt scheduling that changes the context during a sampling.
- With a LoRA, VRAM is still 12.7 GB against 7.3 GB without, and a generation is still about 1.5 to 3 s slower than without.
- The GUI was not operated. No GPU with less than 24 GB.
- The comparison with reForge was not repeated for this version; see docs/v0.29-verification.md (default settings: reForge
  3 to 13 % faster).
