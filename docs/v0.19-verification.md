# v0.19 verification record (2026-11-11)

Goal of this release: less VRAM on the scala-torch backend, and models that are larger than the free VRAM run without a setting.
All numbers: RTX 3090, MCP, fp16, 20 steps, second generation in the same process, memory = peak of `nvidia-smi` minus the value before
the start. scala-torch `0.1.3-gh40`.

## Where the memory went (v0.18, SDXL 1024 x 1024: 11.5 GB)

`SCALATORCH_CUDA_MEMORY_LOG=1` (new) prints a breakdown per session:

- Kept weights: 6.35 GB (U-Net 4.9, text encoders 1.36, VAE 0.09), plus about 0.9 GB of padding: on Windows every driver allocation is
  padded, and a model has thousands of weight tensors.
- U-Net session: 0.44 GB of live tensors, but 2.0 GB held. Freed blocks were reused only for a tensor of exactly the same size.
- VAE decode session: 1.5 GB live, 3.8 GB held.

## Changes

1. **Arena allocator.** Device memory comes from a few large chunks (best fit, split, merge on free), for activations and for kept weights.
2. **Eviction of kept weights.** When the device runs short, kept weights that no open session uses are freed, least recently used first:
   the text encoders make room for the U-Net, the U-Net for the VAE. Weights that were evicted are sent again from a Float16 host copy.
3. **Automatic partial offload.** If the U-Net weights do not fit beside the activations, as many weights as fit stay on the device and the
   rest is sent on every use. Before, offload was a manual switch (`SDFX_SCALATORCH_UNET_OFFLOAD_WEIGHTS=true`) that kept 512 MiB at most.
4. **`SCALATORCH_CUDA_VRAM_LIMIT_MB`** caps the device memory of the worker (all sessions and kept weights). It is also how the small-GPU
   cases below were measured on a 24 GB card.

Images: in all seven single-image runs above (SDXL at none / 8000 / 6500 / 5000 / 4000, SD1.5 at none / 2000) the first and the second

The limit is not exact: the worker's memory outside the tracked chunks (CUDA context, cuBLAS, kernel modules) is assumed to be 600 MiB.

## Found and removed before the release

A variant kept more offloaded weights and gave them up when activations needed the room. It was faster (SDXL at 4000 MB: 25.0 s), but the
images changed: with the same seed, the first and the second image of a process differed (largest difference 160 of 255; both looked
normal). The cause was not found, so the variant was removed and a fixed reserve of 1280 MiB for the activations is used. The check
"first image = second image = unlimited image" is what found it.

## Speed: what was found, nothing gained yet

- A U-Net pass costs about 97 ms for SD1.5 512 (batch of two) and about 525 ms for SDXL 1024.
- The GPU is the limit, not the JVM: utilisation is about 85 % and the power draw about 300 W while sampling. Caching the driver call
  handles changed nothing measurable.
- SDXL per pass, from the profile: linear layers (cuBLAS, 48 to 59 TFLOPS, near the limit of the card) about 30 %; the rest is spread over
  the convolution GEMM and im2col, the attention score matrix (written, read three times by softmax, read again), bias additions,
  transposes and GroupNorm. No single kernel dominates.

## Tests

- scala-torch: `CudaArenaSuite` (4 tests, no GPU needed: random allocate/free without overlap, merge, trim, fallback). The `ffm` suite on
  the GPU (`testFull`): 86 tests, 85 passed, 1 skipped.
- NUI `testFull`: one failure that does not depend on this change (`PixelScrambleSuite` needs `python/.venv-test`). `PreviewImageLoaderSuite`
  timed out once while the GPU measurements ran at the same time and passed alone (21 of 21).
- Three tests fail in scala-torch with and without this change (checked on the previous commit): `CudaUNetSuite` "invalid conditioning
  and cancellation...", `CudaDiffusionResnetSuite` "residual upload and execution failures...", `CudaDiffusionAttentionSuite` "attention
  validates shapes and score budget...". They expect a budget error that kept weights no longer cause since v0.17.

## Not covered

- No real GPU with less than 24 GB was used; the small-memory cases use the limit variable.
- Larger images on a small limit (for example hires 2048) were not measured.
- No GUI setting for the limit yet (environment variable only). The GUI was not used for these checks.
