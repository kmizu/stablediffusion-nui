# Compile (TensorRT / Inductor) verification (#19, partial)

Ledger target `core:compile`, index 236 (NVIDIA/Stable-Diffusion-WebUI-TensorRT). One AlwaysOn plugin `compile` (hook `compile`); engine side `python/sdfx/compile_accel.py`, Scala side `plugins/.../CompilePlugin.scala`. Status: **partial**, tracked with `Refs #19`: the feature works and is verified, but TensorRT is not faster than the plain U-Net in the measurements below on the available GPU, and several upstream features are not provided.

## What the extension does and what this app does

| Upstream (README) | This app |
|---|---|
| ONNX export, then a TensorRT engine per checkpoint with a "Generate Default Engines" button; presets / advanced profiles; static and dynamic engines | `compile` hook with backend TensorRT (Torch-TensorRT, fp16, min block size, builder optimization level, on-disk engine cache) or Inductor (`torch.compile`, three modes). No separate build step: the first generation at a new resolution / batch size builds a static engine, later ones reuse it |
| `sd_unet` quick setting ("Automatic") chooses the engine | the plugin's **Enabled** box; the engine for the request's shape is built or reused automatically |
| Resolution multiple of 64, batch 1-4 for the default engines; Hires. fix needs an engine for both sizes | any size the model accepts; a Hires. fix pass or another batch size builds its own static engine |
| LoRA must be exported to a TensorRT format first (Export LoRA tab) | TensorRT: LoRAs are refused (weights are baked in). Inductor: LoRAs work (PEFT adapters stay live) |
| `medvram` / `lowvram` break engine builds | offload VRAM modes are refused with a message (`gpu` mode only) |

Other behaviour: the compiled forward replaces `unet.forward` for the length of the generation only and is restored in the engine's `finally`; hooks that patch the U-Net or the sampler loop (FreeU, PAG, HyperTile, ...), ControlNet units and Composable LoRA are refused with a message naming them (only an allow-list of eight hooks that do not touch the U-Net may be combined: Model Keyword, PNG Info Injection, Steps Animation, Temperature Guard, NSFW Checker, Aesthetic Score, VAE Tools, Tokenizer; the real runs exercised the compile hook alone, so these combinations are unit-tested only); the settings are written to the infotext (`Compile backend`, `Compile mode` or `Compile min block size` + `Compile optimization level`) and restored by PNG replay, the MCP inspect tool and the UI; `SDFX_TRT_CACHE` moves the engine cache (default `~/.cache/stablediffusion-nui/tensorrt`); `SDFX_TRT_OPTIONS` (JSON) passes further Torch-TensorRT options for experiments. Dependencies are checked up front with a clear message (`triton` + MSVC `cl.exe` on PATH for Inductor, `torch_tensorrt` + `tensorrt` for TensorRT). Torch-TensorRT 2.7 imports `tensorrt.plugin`, which tensorrt 10.9's wheel keeps in `tensorrt_bindings`; a small import shim aliases it.

## Not provided

Dynamic-shape engines and profile tabs, ONNX export, the Export LoRA tab and LoRA refit, SD 2.x and SDXL Turbo / LCM specific presets, ControlNet and U-Net-patching hooks with compile, offload modes, CPU, an explicit "build engine now" button (the first generation builds), reproducing A1111's `sd_unet` setting. TensorRT results are not reproducible bit for bit across engine rebuilds (TensorRT tactic timing): a second session that rebuilds the engine gives a slightly different image than the first (seen: mean abs diff vs plain 0.014 and 0.026 for the same SD1.5 shape in two builds). Within one cached engine, results are exactly repeatable.

## Verification run

Environment: RTX 3090 shared with other jobs (GPU lock held for each run), torch 2.7.1+cu128, `triton-windows 3.3.1`, MSVC 14.44 `cl.exe`, `torch-tensorrt 2.7.0`, `tensorrt 10.9.0.34`, installed with `pip install --target` into a scratch directory and put on `PYTHONPATH` (the shared venv was not touched).

- Python: `python/tests/test_compile_accel.py` (normalisation, every refusal, dependency messages, forward swap and restore, reuse per shape, one build per backend). Scala: `CompileSuite` (controls, hook, infotext, replay, bad values) and the inspect-metadata candidate test. Full-suite results are in the commit message.
- Real runs through the official MCP SDK with the built jar (`scripts/dev/check_compile_real.py`, receipts in `outputs/compile-real-{sd15,sdxl}`): SD1.5 `animekawa_v10` 512x512 (LoRA `20_yui`) and SDXL `waiIllustriousSDXL_v170` 832x1216 (Hires. fix 1.25x = 1040x1520, LoRA `20_hinata`), 20 steps, Euler, `gpu` VRAM mode. For each backend: the plain U-Net twice (deterministic), the compiled U-Net twice (the two results byte-identical), Hires. fix, batch of 2, PNG replay through the typed inspect candidate (byte-identical to the compiled image), a plain generation afterwards byte-identical to the first baseline (forward restored), and the refusals (FreeU together with compile; an invalid backend; TensorRT with a LoRA).
  - Mean absolute difference from the plain image (fraction of full scale; the script asserts < 0.05): SD1.5 Inductor 0.0029 (PSNR 43.1 dB), Hires 0.0046, batch 0.0039 / 0.0009; SD1.5 TensorRT 0.026 (26.1 dB), Hires 0.027, batch 0.022 / 0.005. SDXL Inductor 0.0040 (40.6 dB), Hires 0.0040, batch 0.0053 / 0.0144; SDXL TensorRT 0.0038 (41.2 dB), Hires 0.0036, batch 0.0037 / 0.0097.
  - LoRA with Inductor: compiled vs plain with the LoRA 0.0011 (SD1.5) / 0.0063 (SDXL); compiled with vs without the LoRA 0.093 / 0.100 (the LoRA is really applied inside the compiled graph); repeat byte-identical; a plain generation after a compiled LoRA run is byte-identical to one after an uncompiled LoRA run. In SDXL a plain generation after any LoRA use differs from the pre-LoRA baseline by 0.0028; that happens without compile (engine LoRA unload residue, not caused by this feature and not changed by it).
  - Build and run times (first calls; second call at the same shape): SD1.5 Inductor 441 s cold (50 s with a warm Inductor disk cache), then 1.1 s; SD1.5 TensorRT 267 s cold (204 s / 73 s on later runs), then 1.5-1.9 s; Hires and batch-2 shapes build their own (Inductor 26-329 s, TensorRT 68-386 s). SDXL Inductor 40-314 s per shape, TensorRT 140-174 s per shape on the final run.
  - Speed, measured twice. **U-Net only** (`scripts/dev/bench_compile_unet.py`, random weights of the real architecture, batch 2, fp16, median of 30): SD1.5 512x512 plain 53.5 ms, Inductor 48.9 ms (1.09x), TensorRT 68.8 ms (0.78x; 66.6 ms = 0.81x with the C++ runtime, 87.0 ms = 0.62x with the global partitioner; builder optimization level 5 was abandoned after 13 minutes without finishing a build); SDXL 1024x1024 plain 288.7 ms, Inductor 264.8 ms (1.09x), TensorRT 255.4 ms (1.13x). **End to end through the app** (one 20-step call incl. text encoding, VAE decode and saving; the GPU is shared so these are noisy): SD1.5 plain 1.38 s, Inductor 1.11 s (1.24x), TensorRT 1.60 s (0.86x); SDXL plain 6.49 s, Inductor 6.21 s (1.05x), TensorRT 17.64 s (0.37x). The SDXL TensorRT end-to-end slowdown against 1.13x for the U-Net alone was not explained (VRAM pressure from the engine next to the pipeline on a shared card is the suspect; not investigated further). Conclusion: Inductor gives a small, real gain; TensorRT through Torch-TensorRT is **not an acceleration** on this GPU at these sizes (the plain path already uses fused SDPA attention), so the issue's "acceleration" goal is not met and the work stays partial.
- Images viewed (contact sheets of baseline, Inductor, TensorRT, Hires, LoRA plain and LoRA Inductor): SD1.5 lion and tiger in a forest, SDXL lion portrait. Inductor images are visually indistinguishable from the plain ones; TensorRT keeps the composition and quality but small details move (cub positions in SD1.5, mane strands in SDXL). LoRA plain and LoRA Inductor are the same picture; the LoRA changes the style strongly in both.

The allow-list of combinable hooks was narrowed (from 18 to 8 names) after the real runs; the real runs only used the compile hook alone and the FreeU refusal, whose behaviour is unchanged.

Not verified: the JavaFX form was not driven by hand (controls, replay and infotext are unit-tested), SD 2.x / inpainting / refiner models, ControlNet (refused by design), the offload modes (unit-tested refusal only), Linux, other GPUs, dynamic shapes, cancelling a build in the middle of a TensorRT compile (the cancel check runs before each pipeline call, not inside the build).
