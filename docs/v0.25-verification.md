# v0.25 verification record (2026-11-12)

Goal: close the last structural gap to reForge: attention that does not write a score matrix to memory. scala-torch `0.1.3-gh45`.
All numbers: RTX 3090, MCP, fp16, 20 steps, Euler a, second generation in the same process, on the extracted ZIP (path with a space),
cuDNN from a PyTorch installation unless stated. v0.24 and v0.25 were measured in the same run.

## Change

Float16 self-attention runs through new tensor-core kernels (`h_attention_fused_*`). A warp takes 1, 2 or 4 tiles of 16 query rows of
one head and goes over the keys once, 16 at a time: scores, an online softmax and the product with the values, all in registers.
Nothing of the size queries x keys is written to or read from device memory. Before, cuBLAS wrote the score matrix, softmax read and
rewrote it, and cuBLAS read it again (268 MB per image and layer for SD1.5 at 64 x 64).

- The kernels depend on where the tensor-core fragments keep their elements. This is measured once per session and the kernels are
  used only when the layout is the expected one. On the RTX 3090 the result and the first operand share their positions and a row
  lives in four neighbouring lanes.
- Used for self-attention with widths 40 to 80 that are multiples of 8 (40, 64 and 80 in SD1.5 and SDXL) and query and key counts
  that are multiples of 16. Cross-attention (77 keys), width 160 and other shapes keep the cuBLAS path.
- `SCALATORCH_CUDA_FUSED_ATTENTION_HALF=0` switches it off.

Why five earlier variants failed (see the v0.24 record): their loops over chunks had run-time bounds, so the compiler kept the
fragments in local memory instead of registers. Every variant took about 6.5 ms for `[16,4096,40]` whatever it did. With one kernel
per chunk count and constant loop bounds the same algorithm takes 1.1 ms.

| Shape (heads x batch, tokens, width) | cuBLAS path | fused |

| `[16,4096,40]` (SD1.5 64 x 64, one image) | 3.08 ms | 1.09 ms |
| `[64,4096,40]` (SD1.5 64 x 64, batch of 4) | 12.4 ms | 3.95 ms |
| `[16,1024,80]` | 340 us | 157 us |

With guidance until 70 % of the steps and DeepCache (interval 3): SD1.5 batch size 8 7.1 s, SDXL 5.4 s, SDXL batch size 2 9.6 s.

Batch scaling on v0.25 (SD1.5 512): 1 image 1.7 s, 4 images 4.5 s, 8 images 7.9 s, that is 1.0 s per image at batch size 8.

No request failed and the file counts were right.

## Images

- SDXL, same seed, v0.25 against v0.24: mean difference 2.6 of 255, largest 176; looked at side by side: same image, differences in
  fine detail. The SD1.5 image was looked at as well.
- VRAM limits: the first and the second image at 8000 MB (10.6 s, 7.5 GB) and 4000 MB (19.8 s, 3.6 GB) for SDXL and at 2000 MB (6.4 s,
  1.1 GB) for SD1.5 are pixel-identical to the unlimited image.

## Tests

- `CudaHalfSuite` "fused attention": every kernel variant (1 / 2 / 4 query tiles per warp x 3 / 4 / 5 chunks, widths with and without
  a remainder, large scores, 4096 keys) against Float32, and shapes that must not use the kernel (widths 33 and 50 would be misaligned;
  a first version that accepted them stopped with a misaligned-address error). "tensor-core fragment layout of this device" prints the
  measured layout.
- `ffm` `testFull` on the GPU with cuDNN, fused attention on and off: 94 total, 92 passed, 2 skipped, both times; `CudaHalfSuite` with
  1 and with 4 query tiles forced: 16 of 16.

## Not covered

- Only the RTX 3090 (CUDA compute capability 8.6). On a GPU with another fragment layout the cuBLAS path is used; that fallback was
  not run on such a GPU.
- Width 160 (the 8 x 8 and 16 x 16 levels of SD1.5) and cross-attention are not fused; they are a small part of the time.
- The GUI was not used. No GPU with less than 24 GB.
