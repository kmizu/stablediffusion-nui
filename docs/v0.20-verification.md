# v0.20 verification record (2026-11-12)

Goal: faster generation on the scala-torch backend, most of all with a batch size above 1. scala-torch `0.1.3-gh41`.
All numbers: RTX 3090, MCP, fp16, 20 steps unless stated, second generation in the same process. The machine is shared with a desktop
session and timings move by 10 to 20 % between hours, so every comparison below was measured alternately in the same hour.

## What was wrong

With `batch_size` N the N images were sampled one after another. Measured on v0.19, SD1.5 512 x 512: batch size 1 / 2 / 4 / 8 = 2.4 / 4.8 /
9.6 / 19.2 s, exactly linear.

## Changes

1. **Batched sampling.** A plain txt2img group samples its `batch_size` images together: one U-Net batch of 2N per step (negative and
   positive conditioning for all N images). Each image keeps its seed and its own noise stream. `SCALATORCH_BATCHED_SAMPLING=0` turns it
   off.
2. **Convolution of a batch as one matrix product** (Float16, 3x3): one im2col, one cuBLAS call and one axis swap instead of one cuBLAS
   call per sample. `SCALATORCH_CUDA_MERGED_CONV=0` turns it off.
3. **Kernels.** GroupNorm statistics use 1024 threads per group for wide groups (a `[2,320,64,64]` GroupNorm: 98.6 -> 63.0 microseconds);
   softmax finds the maximum and the sum in one read of the score matrix.

## Measured

Development build against the v0.19 package, alternately, two rounds:

| Request | v0.19 | v0.20 |
| --- | --- | --- |
| SD1.5 512, 1 image, 40 steps | 4.0 / 4.1 s | 3.8 / 3.9 s |
| SD1.5 512, batch size 4 | 8.5 / 9.0 s | 7.3 / 7.4 s |
| SDXL 1024, 1 image | 10.8 / 11.1 s | 10.4 / 10.5 s |

Batched sampling alone (same build, switch on / off): batch size 4: 7.5 s against 8.5 to 8.8 s; batch size 8: 14.3 to 14.8 s against 16.7 s.

On the extracted v0.20 ZIP (path with a space, no `SDFX_*` variables): SD1.5 512 batch size 1 / 2 / 4 / 8 = 2.3 / 3.8 / 7.0 / 13.9 s;
SDXL 1024 batch size 1 / 2 = 10.2 / 19.3 s; SD1.5 count 4 = 6.6 s; count 2 x size 4 = 13.7 s. No request failed; the file counts were
right (4, 8, 16 and 16 files for two requests each).

## Why the gain is 12 to 18 % and not a multiple

A U-Net pass scales almost linearly with the batch: about 12 ms fixed plus 41 ms per image (SD1.5 512). The time is GPU arithmetic, not
per-call overhead: 950 kernel launches per pass cost 11 microseconds each on the CPU (13 % of a pass), GPU utilisation is about 85 % and the
power draw about 300 W. A 3x3 convolution spends about a third of its time in im2col and reaches 23 to 37 TFLOPS in the product, where the
large linear layers reach 48 to 59. Closing the rest of the distance to a cuDNN-based engine needs a convolution without im2col and an
attention that does not write the score matrix to memory; neither is in this release.

## Images

- Float32, batch size 4: the four images of the batched path equal the sequential ones (largest difference 1 to 2 of 255), so seeds and
  noise streams are right.
- Float16, batch size 4: same composition, differences in fine detail (mean 0.4 to 1.5 of 255 for SD1.5, 0.9 to 2.1 for SDXL; edges,
  ribbons, lace). Float16 results depend on the batch a tensor is computed in. Side-by-side sheets for SD1.5 (Euler a, DPM++ 2M) and SDXL
  were looked at; the eight images of the package run (count 2 x size 4) and the single SD1.5 and SDXL images were looked at too.
- Single images changed slightly against v0.19 (changes 2 and 3). With a VRAM limit they are still pixel-identical to the unlimited image
  of v0.20, first and second image: SDXL at 8000 and 4000 MB, SD1.5 at 2000 MB. Memory use is as in v0.19 (SDXL 8.7 GB without a limit,
  7.6 GB at 8000 MB, 3.6 GB at 4000 MB).
- The same request twice gives identical images on the batched path (batch size 2, 4, 8 for SD1.5; 2, 4 for SDXL).

## What takes the batched path

Plain txt2img with Float16 on the GPU, all samplers. Sequential as before: LoRA, ControlNet, hires fix, img2img and inpaint, active hooks,
variation seeds, `eta`, prompt editing between steps, intermediate recorders, Float32, CPU, and while device memory is short. If the batch
does not fit (tested with a session budget of 700 MB and batch size 8: "allocation budget exceeded"), the group is sampled sequentially and
the 16 images equal the sequential run.

Different from the sequential path: one progress event per step for the whole group, and the live preview shows the first image of the
group.

## Tests

- scala-torch: batch of 3 against three single predictor calls (Float32, tiny U-Net, < 1e-4); batch against single pipeline runs for 13
  samplers (largest error 6.3e-5 in the reduced matrix); batched convolution cases (padding, stride, dilation, 5x3 kernel, 3 and 5
  samples); broadcast add, wide GroupNorm and softmax cases. `ffm` `testFull` on the GPU: 90 total, 88 passed, 2 skipped.
- `models` `testFull`: 733 total, 518 passed, 10 failed, 205 skipped; the same 10 fail without this change (729 total, 514 passed). Three
  are the budget tests named in the v0.19 record, three are VAE / offload tests, and four are tolerance tests that only fail in a full run
  (an earlier suite switches the process to Float16) and pass alone.

## Not covered

- Float32 with batched sampling is slower (57 s against 27 s for four SD1.5 images: the attention leaves its cuBLAS path at a U-Net batch
  of 8), so it is off for Float32.
- Cancelling during a batched group and a real out-of-memory on the device (only the budget failure) were not exercised.
- DPM2 (non-ancestral) and DPM++ 2M SDE Heun were not compared.
- The GUI was not used for these checks.
