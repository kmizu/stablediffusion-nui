# v0.21 verification record (2026-11-12)

Goal: faster convolution on the scala-torch backend. scala-torch `0.1.3-gh42`.
All numbers: RTX 3090, MCP, fp16, 20 steps unless stated, second generation in the same process; comparisons were measured alternately in
the same hour.

## Change

1. **cuDNN is used when it is installed.** Float16 convolutions with a kernel larger than 1x1 run through cuDNN instead of the built-in
   im2col + matrix product. cuDNN is not in the ZIP. It is searched in this order: the directory in `SCALATORCH_CUDNN_PATH`, the CUDA
   Toolkit (`CUDA_PATH`), the cuDNN installer's directory under Program Files (`NVIDIA\CUDNN\v9.x\bin\...`), and the directories of
   `Path`. cuDNN 9 and 8 are recognised. Without cuDNN everything works as in v0.20. `SCALATORCH_CUDNN=0` turns it off.
   Only a directory that holds the front library and its parts is used: a front library without its parts ends the process when it is
   called (seen during development: "Could not locate cudnn_ops64_9.dll").
2. **Kept weights are evicted per model.** With a VRAM limit, a half-evicted U-Net kept 4.7 GB of chunks for 1.4 GB of tensors and was
   then run offloaded although it would have fitted.

## Measured

Convolution alone (microseconds per call, fastest of seven runs): 3x3 `[2,320,64,64]` 562 -> 186; `[8,320,64,64]` 2383 -> 950;
`[2,640,32,32]` 443 -> 181; `[8,640,32,32]` 1494 -> 804; `[8,1280,16,16]` 1265 -> 792.

Same build, cuDNN on / off, two rounds:

| Request | off | on |
| --- | --- | --- |
| SD1.5 512, 1 image, 40 steps | 3.7 / 3.8 s | 3.5 / 3.6 s |
| SD1.5 512, batch size 4 | 7.1 / 7.2 s | 5.9 / 6.3 s |
| SDXL 1024, 1 image | 10.6 / 11.0 s | 8.8 / 9.1 s |

On the extracted v0.21 ZIP (path with a space), cuDNN from `SCALATORCH_CUDNN_PATH` (cuDNN 9 of a PyTorch installation), against the v0.20
package in the same run:

| Request | v0.20 | v0.21 without cuDNN | v0.21 with cuDNN |
| --- | --- | --- | --- |
| SDXL 1024, 1 image | 10.0 s | 10.0 s | 8.7 s |
| SD1.5 512, 1 image | not measured in this run | 2.1 s | 2.0 s |
| SD1.5 512, batch size 4 | 7.1 s | 7.0 s | 6.1 s |
| SD1.5 512, batch size 8 | not measured in this run | not measured | 11.7 s |
| SD1.5 512, count 4 | not measured in this run | not measured | 5.6 s |

(v0.20 on its release day: batch size 8 13.9 s, count 4 6.6 s; not the same hour.)

With a VRAM limit and cuDNN (SDXL 1024): 8000 MB: 10.2 s and 7.4 GB; 4000 MB: 20.0 s and 3.6 GB; in the development build also 6500 MB:
13.6 s and 6.0 GB (v0.20: 18.5 s). No request failed.

## Images

- cuDNN computes the convolution in a different order, so Float16 images differ in fine detail from the images without it (mean
  difference 3.4 to 4.5 of 255, same composition). The SDXL and the SD1.5 image with cuDNN were looked at.
- With cuDNN, the first and the second image at 8000 and 4000 MB are pixel-identical to the unlimited cuDNN image; without cuDNN, the
  first and second unlimited images are identical as well.

## Tests

- `CudnnSuite`: only complete installations are candidates, in the documented order (no GPU needed).
- `ffm` `testFull` on the GPU, once with cuDNN and once with `SCALATORCH_CUDNN=0`: 91 total, 89 passed, 2 skipped, both times. The
  convolution cases of `CudaHalfSuite` (padding, stride, dilation, 5x3 kernel, grouped, batches of 3 and 5) compare the Float16 result with
  the Float32 one, so with cuDNN they check cuDNN.

## Not covered

- Only cuDNN 9 (9.x of a PyTorch 2 installation, CUDA 12) was run. The cuDNN 8 names are recognised but were not run.
- A cuDNN built for another CUDA major version than the installed driver supports was not tried.
- 1x1 convolutions still use the built-in path.
- The GUI was not used for these checks, and there is no GUI setting for the cuDNN directory.
- Found, not fixed: cuBLAS is not in the ZIP either; it is loaded from the CUDA Toolkit (`CUDA_PATH`). On a PC without the Toolkit the
  Float16 path has no cuBLAS. This was not tested on such a PC.

## v0.22: settings for the cuDNN folder and the VRAM limit (2026-11-12)

Settings > Engine has two new optional fields, `scala-torch cuDNN folder` (`scala_torch_cudnn_dir`) and `scala-torch VRAM limit (MB)`
(`scala_torch_vram_limit_mb`). They reach the worker as `SCALATORCH_CUDNN_PATH` and `SCALATORCH_CUDA_VRAM_LIMIT_MB`; an environment
variable of the same name wins. scala-torch is unchanged (`0.1.3-gh42`).

Test: `ScalaTorchLaunchSuite` "zero configuration..." checks that the variables are absent when unset, set from the settings, overridden
by the environment, and absent for a limit of 0. NUI `test`: one failure that does not depend on this change (`PixelScrambleSuite` needs
`python/.venv-test`).

On the extracted v0.22 ZIP, values written to `settings.json`, SDXL 1024, 20 steps, second run: no settings 9.7 / 9.9 s and 8.7 GB; cuDNN
folder 8.7 s and 9.8 GB; cuDNN folder and limit 4000: 19.8 s and 3.6 GB. With cuDNN and no limit the memory use varied between runs (7.5,
8.5 and 9.8 GB were seen); the cause (cuDNN's own allocations or its workspace for the VAE) was not examined.

Not covered: the two fields were not operated in the GUI; the values were given through `settings.json`.
