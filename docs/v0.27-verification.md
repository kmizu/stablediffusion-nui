# v0.27 verification record (2026-11-12)

Goal: the time outside the sampling steps, where a single image was losing most against PyTorch. scala-torch `0.1.3-gh48`.
All numbers: RTX 3090, MCP, fp16, 20 steps, Euler a, second generation in the same process, on the extracted v0.27 ZIP (path with a
space), cuDNN from a PyTorch installation.

## What was found

For one SD1.5 image the two engines differ little per step and a lot outside the steps (v0.26, from runs with 1, 20 and 60 steps):
a step costs 62 ms in scala-torch and 57.5 ms in the PyTorch engine; the rest of a generation takes 0.5 to 0.6 s against 0.3 s.
Live previews are not the cause (the same with previews off, in both engines). While sampling, the GPU is 80 to 90 % busy.

The session log (`SCALATORCH_CUDA_LAUNCH_STATS=1`, now with start and end times) showed three text encoder sessions per generation
with 45 to 50 ms between them, about 0.2 s together, although the prompts had not changed.

## Changes

1. **Text encoder results are kept.** A run with the same token embeddings, layers and weights is answered from memory; generating
   again with the same prompts starts no text encoder session. `SCALATORCH_CLIP_CACHE=0` switches it off.
2. **The cuDNN handle is kept between sessions** (per device and thread, like the cuBLAS handle), with its convolution plans.
3. **Attention reads the heads in place.** The fused kernels take the projections as they are ([batch, tokens, heads x width]), so
   the four transposed copies per attention layer are gone. Bit-identical to the old call; no measurable change in time.

## Measured

v0.27 against the PyTorch engine (diffusers 0.33.1, PyTorch 2.7.1, cuDNN 9.7), same requests, alternately, two rounds:

| Request | PyTorch engine | scala-torch v0.27 |
| --- | --- | --- |
| SD1.5 512, 1 image | 1.3 / 1.3 s, 3.6 GB | 1.6 / 1.6 s, 3.0 GB |
| SD1.5 512, batch size 4 | 4.1 / 4.2 s, 7.1 GB | 4.4 / 4.4 s, 3.0 GB |
| SD1.5 512, batch size 8 | 7.9 / 7.9 s, 11.8 GB | 7.8 / 7.9 s, 3.4 GB |
| SDXL 1024, 1 image | 6.8 / 6.9 s, 16.2 GB | 7.4 / 7.5 s, 7.2 to 8.6 GB |

- Batch size 8: the same time. Batch size 4: 6 % slower. SDXL: 9 % slower. One SD1.5 image: 0.3 s slower (v0.25: 0.5 s).
- Memory: a third to a half of the PyTorch engine's.

This is still not a measurement of reForge, which is not started in this project.

Development build, same hour: SD1.5 1 image 1.7 s with the text encoder cache off and 1.6 s with it on.

## Images

With the text encoder cache on and off, the first and the second image are pixel-identical (SD1.5 512 and SDXL 1024, largest
difference 0).

## Tests

- `CudaHalfSuite` "tokens-major attention equals heads-major attention on transposed copies": six shapes covering every kernel
  variant, one to three batch members, bit for bit; shapes that must be refused (77 keys, width 160, width 50).
- `ffm` `testFull` on the GPU with cuDNN: 96 total, 94 passed, 2 skipped; with the fused attention switched off: 93 passed, 3 skipped.
- Touched `models` suites (U-Net, image pipeline, DeepCache, CLIP, parallel count): 45 total, 38 passed, 6 skipped, 1 failed (the
  `CudaUNetSuite` budget test that fails without this change).

## Not covered

- The text encoder cache has no test of its own; it was checked by the pixel comparison above and by the session log (no text encoder
  session in the second generation). A LoRA on the text encoder bypasses the cache; that case was not run.
- Where the remaining 0.3 s of a single SD1.5 image goes was not measured further (about 0.25 s lies outside the GPU sessions).
- reForge was not run. The GUI was not used. No GPU with less than 24 GB.
