# v0.28 verification record (2026-11-12)

Goal: one switch for the speed-ups that change the image a little, decided by the owner ("keep them optional and add a fast preset").
scala-torch `0.1.3-gh49`. All numbers: RTX 3090, MCP, fp16, 20 steps, Euler a, second generation in the same process, on the extracted
v0.28 ZIP (path with a space), cuDNN from a PyTorch installation.

## Change

New built-in plugin **Fast mode** (`fast_mode`, off by default). Switched on, it adds two things to a request unless the request
already has them:

- DeepCache: a full U-Net step every 3 steps, 5 full steps first (Ma et al., CVPR 2024);
- CFG for the first 70 % of the steps only: the CFG steps from the request's value to 1, and at 1 the engine does not compute the
  negative prompt (after Kynkäänniemi et al., "Applying Guidance in a Limited Interval", 2024).

Two controls: "CFG until" (0.3 to 1, 1 = all steps) and the DeepCache interval (0 = no DeepCache). The DeepCache and CFG Schedule
plugins keep their own values when they are switched on. Both parts need the scala-torch engine features `deepcache` and
`cfg_schedule`.

scala-torch gh49 against gh48 (v0.27): measurement tools and three options that are off by default (packed attention projections,
cross-attention context cache, cuDNN algorithm by measurement); none of them changed a generation time when switched on.

## Measured

Same package, plain against Fast mode, two rounds:

| Request | plain | Fast mode |
| --- | --- | --- |
| SD1.5 512, 1 image | 1.5 / 1.5 s | 1.2 / 1.2 s |
| SD1.5 512, batch size 4 | 4.3 / 4.3 s | 3.3 / 3.4 s |
| SD1.5 512, batch size 8 | 7.7 / 7.7 s | 5.9 / 6.0 s |
| SDXL 1024, 1 image | 7.3 / 8.0 s | 4.3 / 4.5 s |
| SDXL 1024, batch size 2 | 13.9 / 14.5 s | 8.0 / 8.2 s |

No request failed; the file counts were right. The saved PNG carries `Fast mode: "CFG until 0.7, DeepCache interval 3"`.

For comparison, reForge itself on this PC earlier the same day (see the v0.27 record; not the same minutes): 1.4 s, 4.3 to 4.4 s, 7.6 to
8.3 s, 7.1 to 7.3 s and 14.0 to 14.1 s. With default settings SDNUI is close to reForge or slower (between sessions SDNUI's own times
moved by 5 to 10 %); with Fast mode it is faster than reForge's default in every row, at the price of a changed image.

## Comparison with reForge from a cooled GPU (added after the release)

The earlier comparisons did not control the GPU temperature. The same reForge request takes about 20 % longer on a hot GPU: started
at 47 degrees it gave 1.2 / 3.6 / 6.9 / 6.0 / 11.6 s, at about 70 degrees 1.4 / 4.3 to 4.5 / 7.6 to 8.4 / 7.1 to 7.4 / 14.0 to 14.1 s
(SD1.5 512 batch size 1 / 4 / 8, SDXL 1024 batch size 1 / 2). So the sentence above, "close to reForge or slower", rests on
measurements that were not comparable.

Repeated with every measurement started only after the GPU had cooled to 52 degrees or less (51 to 54 measured), reForge resident on
port 7869 (API mode, "Using pytorch attention"), SDNUI v0.28 from the extracted ZIP, two rounds, the order of reForge and SDNUI
swapped in the second round. reForge: second and third generation; SDNUI: second generation.

| Request | reForge | SDNUI plain | SDNUI Fast mode |
| --- | --- | --- | --- |
| SD1.5 512, 1 image | 1.2 / 1.4 to 1.5 s | 1.6 / 1.8 s | 1.4 / 1.4 s |
| SD1.5 512, batch size 4 | 4.5 / 4.3 to 4.4 s | 5.1 / 5.2 s | 3.9 / 3.4 s |
| SD1.5 512, batch size 8 | 8.4 to 8.5 / 7.8 s | 9.0 / 8.3 s | 6.9 / 6.9 s |
| SDXL 1024, 1 image | 6.3 to 6.7 / 7.8 s | 9.0 / 8.9 s | 5.3 / 4.7 s |
| SDXL 1024, batch size 2 | 14.5 to 14.7 / 12.4 to 12.5 s | 16.9 / 14.9 s | 9.8 / 8.3 s |

SDNUI alone afterwards (reForge stopped, same cooling rule, two rounds): 1.9 / 1.7 s, 4.3 / 4.8 s, 9.0 / 8.9 s, 8.6 / 8.6 s and
16.2 / 16.3 s. The resident reForge process was therefore not what slowed SDNUI in the table.

What this shows:

- With default settings SDNUI is slower than reForge in every row: about 5 to 15 % for the SD1.5 batches, 15 to 40 % for one image,
  15 to 35 % for SDXL.
- Fast mode is faster than reForge's default for batches and for SDXL (about 15 to 35 %) and equal for one SD1.5 image; the image
  changes (see "Image").
- SDNUI's plain times in this session are 10 to 20 % above the table at the top of this record (1.5 / 4.3 / 7.7 / 7.3 to 8.0 /
  13.9 to 14.5 s), measured the same day on the same package. The cause was not found. About 2.3 GB of VRAM was in use by other
  programs before the last run; whether that matters was not tested. reForge moved by up to 20 % between the two rounds as well
  (SDXL 6.3 to 7.8 s).
- Not measured: reForge with its own speed options, more than two rounds, another GPU.

reForge was started for the measurement only and stopped afterwards (no listener on port 7869); `git status` of its working tree is
the same as before.

## Image

SDXL, same seed, plain and Fast mode side by side, looked at: the same composition; Fast mode is softer, the ribs of the knitted
sweater are fainter and the eye colour differs (yellow against grey; the prompt names no eye colour). It is a draft mode: switch it off
for a final render.

## Tests

- `FastModeSuite` (4 tests): off by default and registered after DeepCache and CFG Schedule; the default hooks and their values; hooks
  that are already set keep their values; each part can be left out.
- NUI `test`: one failure that does not depend on this change (`PixelScrambleSuite` needs `python/.venv-test`).
- scala-torch gh49: `ffm` `testFull` on the GPU with cuDNN 96 total, 94 passed, 2 skipped; the touched `models` suites 15 total,
  9 passed, 5 skipped, 1 failed (the `CudaUNetSuite` budget test that fails without these changes).

## Not covered

- The plugin was driven through MCP (`always_on: {"fast_mode": {"enabled": true}}`); its panel was not operated in the GUI.
- Restoring Fast mode from a PNG's infotext is not implemented (the key is written, not read back).
- Fast mode was run with Euler a and the default values only. With LoRA, ControlNet or hires fix the request leaves the batched path;
  DeepCache refuses ControlNet.
- The Python engine was not tried with this plugin.
- No GPU with less than 24 GB.
