# v0.15 verification record (2026-11-10)

## "Generating ..." never finishes (user report)

Cause found in the user's installed copy (`D:\dev\SDNUI\config\settings.json`): `scala_torch_unet_device = cpu`, `scala_torch_vae_device = cpu`,
`dtype = fp32`, `vram_mode = cpu`, engine backend `auto`. Earlier versions started the scala-torch engine with device `cpu` as the default, and the app forced
`dtype fp32 / vram_mode cpu` in memory and wrote those values to settings.json. Since v0.11 the packaged app starts on scala-torch, so the saved values
made every generation run on the CPU (minutes per image), which looks like a hang. The new device default `auto` (CUDA when present) never applied because
the old `cpu` was stored explicitly.

Fix: `Settings.migrateNativeDefaults` runs once at start. When both devices are the old default `cpu`, they become `auto`; when the forced pair
`fp32` / `cpu` is found, dtype and VRAM mode go back to the normal defaults; the settings file is rewritten and marked (`native_defaults_version = 1`).
Choices that cannot be the old defaults (for example `cuda:1`) are kept. The engine log now says which devices and precision the native engine uses
(`[sdfx] scala-torch: U-Net cuda, VAE cuda, precision fp16`) and warns when it runs on the CPU.

Checks: `SettingsMigrationSuite` (3 tests: repair, kept choices, old file without the field), `engine` / `ui` / `mcp` / `scalaTorchEngine` suites.
Real check on the extracted v0.15 ZIP: the user's real settings.json was copied into the package home; the first start rewrote it
(`dtype fp16, vram_mode gpu, devices auto, native_defaults_version 1`), the engine log printed `U-Net cuda, VAE cuda, precision fp16` and SD1.5
512x512 / 20 steps took 4.3 s (warm) through MCP instead of running on the CPU.
Also checked with the real MainWindow harness (`RealPromptToolsCheck`, SD1.5 and SDXL, several generations): no hang with the v0.14 engine.

Note: MCP started with plain `java -cp ...` and engine backend `auto` uses the Python engine when it is in the jar; the packaged `SDNUI.exe` sets the
scala-torch default itself. Not verified: the GUI of the user's machine (only the settings it loads and the headless engine).
