# v0.17 verification record (2026-11-10)

## Batch count ("count") runs in parallel

Request: with Batch count N > 1 the images were generated one after another. Wanted: count 2 / size 4 = 2 parallel streams of 4 images, count 4 / size 2 =
4 parallel streams of 2 images (count = parallel streams, size = images per stream).

Finding: the native engine generated every image of `batch_size x n_iter` one at a time, and every image opened new CUDA sessions that uploaded the model
weights again (SD1.5: about 2 s of a 4.4 s image). So parallel streams alone could not have helped: they would have uploaded the weights N times.

Changes (scala-torch `0.1.3-gh36`):
1. **Device-resident shared weights** (`CudaWeightPool`): the weights of the U-Net, VAE and text encoder stay on the GPU between sessions and are shared by
   the sessions of all threads (views of the same device memory). They are freed after `SCALATORCH_CUDA_KEEP_CONTEXT_SECONDS` (default now 60) without a
   session, or when the model changes or is unloaded. LoRA adapters and the merged LoRA weights stay private to a session.
2. **Parallel count** (`NativeParallelCount`): the `n_iter` groups of a plain txt2img request run as separate requests on their own threads and CUDA streams
   (at most `SDFX_SCALATORCH_PARALLEL_COUNT_MAX`, default 4; 1 = off), with seeds shifted by the group offset, progress events renumbered for the whole job,
   and a group that fails with a memory error repeated alone afterwards. Requests with LoRA, ControlNet, embeddings, other hooks, prompt tags or unknown
   options, CPU execution and count 1 stay on the sequential path (their state is per request). The model keyword hook (always sent) is allowed when it
   changes no prompt.

Checks: scala-torch `CudaHalfSuite` (shared weights: first upload, reuse by a later session and by another thread, separate Float32 entry, re-upload after
release) and `NativeParallelCountSuite` (groups, seeds, renumbered progress, what is not split, memory-error retry). Output equality: SD1.5 count 4 x size 2
with seed 173 generated seeds 173..180; parallel and sequential runs give **identical pixels (max difference 0)**.

Measured on the extracted v0.17 ZIP (RTX 3090, MCP, clean environment, SD1.5 `animekawa_v10` 512x512, 20 steps, second run; "before" = sequential):

| Request (images) | v0.16 | v0.17 sequential (weights stay on the GPU) | v0.17 parallel | GPU memory (job) |
| --- | --- | --- | --- | --- |
| count 4 x size 1 (4) | 16.0 s | 9.3 s | **6.9 s** | 3.7 -> 7.6 GB |
| count 2 x size 4 (8) | about 32 s | 19.2 s | **15.1 s** | 3.7 -> 5.0 GB |
| count 4 x size 2 (8) | about 32 s | 18.2 s | **13.8 s** | 3.7 -> 7.6 GB |

SDXL 1024x1024, count 2 x size 2 (4 images): sequential 44.2 s, parallel 40.2 s (GPU memory +3.9 GB). The GPU is already busy with one stream, so parallel
streams add 10 to 25 % on top of the shared weights, which give the larger part of the speed-up.

Not covered: the GUI itself (the same engine request was used through MCP), LoRA / ControlNet batches (sequential by design), GPUs with less memory (a group
that does not fit is repeated alone, tested with a fake memory error only).
